# 경쟁자 정황 검증 + GBM 비용헤드 실험 판정 (2026-08-19)

공개 저장소의 최신 실험 기록을 확인해 두 경쟁팀의 "릿지+GBM 앙상블"이 실제로
우리보다 나은지 검증했다. 그리고 우리 베이스(T38)에 그 메커니즘을 **복제해**
dev 점수에 미치는 영향을 직접 측정했다. 경쟁사 실험 코드는 복사하지 않고
아이디어(hashed 특징 위 비선형 비용 회귀)만 적용했다.

## 1. 이 각각 비교의 전제

우리의 "Dev 0.683892"는 `data/materialized/dev`(공식 880문항)에서의 측정이고,
경쟁팀도 같은 공식 dev를 쓴다(각각 `data/dev/outcomes.json` 880문항). 둘 다
Train(1760)으로 학습 → 공식 dev로 측정하므로 절대 비교가 성립한다.

## 2. 두 경쟁팀 실측

| 팀 | 정책 | 공식 dev | 비고 |
| --- | --- | ---: | --- |
| thislifehea | 릿지(H, margin 튜닝) | 0.695994 | 이게 08-14 기준 실제 채택 |
| thislifehea | **릿지+GBM 앙상블(K)** | **0.701591** | 실험 기록상 raw 최고; **채택 여부 미정**(안전마진 남음 문제) |
| 원숏 | 공식 hash_regex baseline | 0.695369 | |
| **우리** | **T38 (q0.68+urb1.2)** | **0.683892** | 이미 제출·이미지 배포됨 |
| 우리 최고 해본 것 | t5-hash-h075 | 0.692330 | Train-CV premium overflow로 폐기, 채택 안 됨 |
| yuJunhyk | v1.3 linear (게이트 통과) | 0.6759 | "0.6920"은 **dev 오염** — 정직한 수준은 0.68 안팎 |

- **thislifehea K(+0.0056 over H)**는 score/cost **둘 다** 릿지와 GBM을 평균한
  앙상블에서 나왔다. 단 그들은 Premium 여유가 얇아(0.55%) 채택을 미뤘고, 실제
  최종 채택은 관측 08-14 기준 H(0.695994)였다. 08-19 기준 새 채택 여부는 미확인.
- **yuJunhyk는 우리 위협이 아니다.** 스스로 dev 오염(과적합) 크기 1.1pp를 실측,
  정직한 수준을 0.6759로 보고했다.
- **진짜 위협은 thislifehea.** 우리가 공식 baseline조차 dev에서 못 이긴다
  (0.6839 vs 0.6954). 단 이 절대치는 "숨은 채점셋은 dev보다 비싸다(공식 baseline
  Premium 3.985→4.2 초과)" 는 사전검증으로 보정돼야 하며, 더 높은 dev 품질이
  위험 보정 후에도 그대로 이기는지는 불확실.

## 3. GBM 비용헤드 실험 (우리 T38 복제)

`experiments/probe_gbm_costgate.py`로 먼저 Train-OOF 로그비용 RMSE를 재고,
`GBMHashRidgeCost`(`gbm_hash_ridge`, `heads.py`)로 전체 파이프라인을 돌렸다.

**OOF 로그비용 RMSE (낮을수록 좋음, Train 5-fold):**
- ridge OOF: 총 0.681
- HistGBM OOF: 총 **0.568** (훨씬 좋음)
- 릿지·GBM 평균(w=0.7): 0.576

**그런데 dev final_score (공식 dev, 같은 T38 게이트·할당·스케어헤드):**
- ridge (현 챔피언): **0.6814**
- GBM 전용 (w=1.0): 0.6773 ▼
- GBM 앙상블 w=0.3/0.5/0.7: 0.6799/0.6788/0.6799 ▼ (전부 ridge 미만)
- 강한 GBM(ml=31,it=150): 0.6822 ≈ (우열 아님)
- Premium만 GBM: 0.6806 ▼

**판정: GBM 비용헤드를 우리 T38에 끼워도 dev 점수가 오르지 않는다.** 단일
모델 OOF RMSE는 GBM이 더 좋지만, 예산 사용량이 내려가고(프리미엄 3.65→3.41)
가격 배율이 달라져 할당이 더 보수적으로 변해 점수가 깎인다. 우리의
risk_quantile/unseen/calibration 머신이 이미 비용 불확실성을 가격에 넣고 있어
GBM이 추가하지 못한다. D8: **기각(추가 실험 없이).**

**왜 thislifehea는 이득을 봤나:** 그들의 +0.0056은 비용헤드가 아니라 **score
헤드까지 포함한 릿지+GBM 앙상블**과 그에 맞춘 안전계수 재탐색에서 나왔다. 우리
score 헤드는 이미 가족 특화로 튜닝돼 있어 두 번째 독립 모델을 섞는 이득이
우리에겐 재현되지 않았다(과거 LightGBM score OOF도 폐기됨, TODO 73).

## 4. 결론과 권고

- **GBM 비용헤드 따라가기 = 소용없음(측정 완료).** 이것이 우리가 지난주에
  "릿지+GBM을 따라가겠다"고 하다 포기한 방향의 확인이다.
- 남은 위협은 thislifehea가 K(0.70대)를 안전하게 제출하는 경우. 우리가 그보다
  낮은 dev(0.68)로 이기려면, dev 품질 그 자체를 끌어올려야지 비용헤드 방식으로는
  안 된다. 짧은 시간 안에 그 점수 차를 메울 설명 가능한 레버는 확인되지 않음.
- **현 방침 유지 권고:** 현재 T38(이미지 제출 완료, 안전 여유+이미지 배포)을
  동결하고 남은 시간은 마진·게이트 임계의 극소 튜닝(dev 대신 Train-OOF 판정)과
  보고서·데모 완성에 쓴다. "0.69~0.70 최고점 추격"은 점수헤드 앙상블 없이는
  수익 대비 위험으로 기각.
