# 결과보고서 원고

공식 양식(osscontest.kr에서 받는 한글/Word 파일)에 옮겨 넣을 내용이다.
본문 5쪽 이내, 첫 쪽의 작성 안내와 회색 안내 문구는 제출 전에 삭제한다.
파일명은 `2026 오픈소스 개발자대회 결과보고서_접수번호(팀명)`.

**제출 전에 채워야 하는 칸은 `⬜`로 표시했다.**

---

## 1. 프로젝트 개요

프롬프트 하나마다 세 모델 중 하나를 고르는 라우터다. 모델을 부르지 않고
**프롬프트 본문과 등급만 보고** 결정하며, 등급별 비용 상한 안에서 정답률
합계를 최대화한다.

| 모델 | 성격 |
| --- | --- |
| `ax31-light` | 가장 싸다. 예산 기준선 |
| `ax31` | 중간 |
| `axk1-think` | 가장 비싸고 정확하다 |

세 등급은 "항상 최저가로 돌렸을 때의 총비용"에 배수를 곱한 예산을 준다.

| 등급 | 예산 배수 | 최종 점수 가중치 |
| --- | ---: | ---: |
| Fast | 1.25배 | 0.40 |
| Balanced | 2.00배 | 0.30 |
| Premium | 4.00배 | 0.30 |

## 2. 문제의 성격

공개 Dev 880문항을 공식 채점기로 재면 문제가 분명해진다.

| 전략 | 정답률 | 가중 최종 점수 | 비고 |
| --- | ---: | ---: | --- |
| 항상 `axk1-think` | **0.8264** | **0.0000** | 세 등급 모두 예산 초과 |
| 항상 `ax31` | 0.6918 | 0.2075 | Fast·Balanced 초과 |
| 항상 `ax31-light` | 0.6193 | 0.6193 | 항상 통과 |
| **제출 라우터** | — | **0.677159** | 세 등급 통과 |

품질 천장은 0.8264인데 살 돈이 없다. **예산을 한 번이라도 넘기면 그 등급은
0점**이므로, 이 문제는 "좋은 모델 고르기"가 아니라 **"제한된 예산으로 무엇을
살지 고르기"**다.

## 3. 접근

세 단계로 나눈다.

**(1) 예측.** 프롬프트에서 14개 정규식 특징과 256-bin signed
unigram/bigram을 뽑아 모델별 점수와 로그비용을 능형회귀로 예측한다. 비용은
계열·모델별 **4-fold 내부 OOF 상대오차 80분위**로 보정해 생성 길이의 heavy
tail을 가격에 넣는다. 위험 통계가 자기 행의 관측 비용을 보고 낙관적으로
맞춰지는 것을 막는다.
점수 ridge는 alpha 32,000의 강한 축소로 lexical 계수 과적합을 줄이며, 학습에서
관측되지 않은 계열은 관측 계열 중 최악의 q90 비용으로 폴백한다.

**(2) 배분.** 문항마다 "이 모델로 올리면 점수가 얼마 오르고 비용이 얼마
드는가"를 계산해 **비용 대비 점수 증가율(ROI)** 순으로 예산이 닿는 데까지
산다. 각 문항의 (비용, 점수) 점들의 **상단 볼록포**만 남기므로 중간에 손해인
선택이 끼어들지 않는다.

라그랑주 승수를 이분 탐색하는 방식과 답이 같으면서 1.7배 빠르고, **순서에
무관함이 자명하다.** 평가에서 문항 ID를 전부 바꾸고 순서를 섞어 다시 돌리는
감사가 있으며, 결과가 하나라도 다르면 자동 채점이 멈춘다.

**(3) 안전.** 비용은 예측값이라 실제와 다르다. 예측이 낮게 나오면 예산을
넘겨 0점이 된다. 그래서 배치 크기에 따른 여유(`h − k/√n`)와 prompt-only
조건부 tail gate를 두고, 6종 분포 변화 시나리오 × 문항 수 3종 × 등급 3종으로
**36,000회 모의 실행**해 초과가 0회인 설정만 챔피언으로 올린다.

## 4. 결과

공개 Dev 880문항, **컨테이너가 낸 출력을 공식 채점기에 넣은** 값이다.

| 등급 | 점수 | 예산 사용 | 한도 |
| --- | ---: | ---: | ---: |
| Fast | 0.652273 | 1.1105 | 1.25 |
| Balanced | 0.681534 | 1.5173 | 2.00 |
| Premium | 0.705966 | 2.5012 | 4.00 |
| **가중 최종** | **0.677159** | | |

Train 5-fold OOF 0.659190. 4/6/8-fold OOF도
0.658608 / 0.658892 / 0.659545로 이전 T17보다 모두 높았다.
leave-one-family-out에서는 아홉 계열을 하나씩 학습에서 완전히 뺐고, 모든 계열의
세 tier가 예산을 통과했다. 결합 OOF는 0.652287이다. 파산 게이트 36,000회 초과
0회. 전체 386개 중 371개 통과, 14개 skip이며 Python 3.14의 기존 오류 메시지
불일치 1건만 남았다. 실험 레코드에는 fold 수를 함께 저장해 재현 가능하게 했다.

숫자 정규화 템플릿을 5% 섞은 후보는 단일 5-fold에서 0.633750이었지만,
4/6/8-fold 효과가 일관되지 않았고 4×3 nested OOF에서 고정 제출 구성보다
0.000227 낮았다. 비공개 평가 분포를 알 수 없으므로 공개 점수의 얇은 개선보다
일반화 근거를 우선해 이 후보의 승격을 취소했다.

이후 공식 hash-regex의 signed unigram/bigram 표현을 참가자 파이프라인에 넣은
공격 후보는 Train OOF 0.6539, Dev 0.6882까지 올랐다. 그러나 공개 Dev의
로그비용 중앙값만으로는 생성비용 heavy tail을 막지 못했고 예산 스트레스에서
탈락했다. 계열별 총합 보정, 상대비용 90분위 pricing, budget tier별 점수
헤드까지 단계적으로 적용했다. 마지막 후보는 OOF 0.633750, Dev 0.648722로
제출 구성보다 높았지만 36,000 tier-scenario 중 Fast가 한 번 예산을 넘었다.
등급 예산을 한 번 넘으면 해당 등급이 0점이므로 이 후보도 채택하지 않았다.
이 결과는 공개 점수 최고값이 아니라 비공개 분포에서 살아남는 정책을 제출한
이유를 보여 준다.

T13에서 실패 trial의 비용 기여를 문항별로 분해하자 초대형 수치, 깊은 LaTeX,
`code_io`의 소수 ax31·K1 선택이 반복 재표집될 때만 파산을 만들었다. 전체
headroom을 줄이는 대신 이 희소 노출만 tier별로 차단했다. cap은 Train OOF로
골랐고, T14는 OOF 0.638409와 Dev 0.669574를 얻으면서 36,000회 초과 0회를
달성했다. 공개 prompt-heuristic 0.655341보다 높고, 공개 Dev에 맞춰 안전계수를
보정한 hash-regex 0.695369보다는 낮다.

T15는 score ridge를 강하게 축소해 T14보다 5-fold OOF를 0.016264 높였다.
첫 후보는 LOFO Premium 4.161, size-200과 extreme shift에서 각각 한 번씩
실패했다. 실패 문항을 분해해 미관측 계열 최악 q90 폴백, `code_io`·`other`
K1 차단, Premium 상대비용 cap 70을 추가했다. 정상 Dev 점수를 유지하면서
LOFO 9/9와 최종 0/36,000을 통과했다.

4×3 nested 선택에서는 작은 inner-train의 비용 추정이 불안정해 alpha=100
대조군을 골랐으므로 nested 통과를 주장하지 않는다. 대신 실제 제출 학습 크기의
4/5/6/8-fold와 LOFO 일관성을 근거로 삼았다. tier별 alpha를 쓴 T16은 단일
5-fold 0.656264였지만 나머지 fold와 Dev가 하락해 선택 과적합으로 폐기했다.

T17은 비용 tail 통계를 같은 학습행의 잔차가 아닌 4-fold 내부 OOF 잔차로
바꿨다. q70/q75와 q80 기본형은 점수가 더 높았지만 파산 게이트에서 탈락했다.
q80의 headroom을 Fast 0.75, Balanced/Premium 0.90으로 조정한 첫 후보도 최종
36,000 판정에서 세 번 경계를 넘었다. 실패 폭과 배치 크기에 맞춰 tier별
`size_penalty`를 2.25/2.5/2.5로 최소 보정한 결과 0/36,000을 달성하면서 T15보다
5-fold OOF +0.003835, Dev +0.006222를 얻었다. LOFO 결합 점수도 0.637912에서
0.652131로 상승했다.

T17도 4×3 nested에서는 alpha=100 대조군이 선택됐다. 강축소 후보가 작은
inner-train에서 예산을 넘긴다는 부정적 증거를 숨기지 않는다. 최종 제출과 같은
전체 Train 규모의 4/5/6/8-fold 일관성, 9개 family LOFO, 36,000회 스트레스를
종합해 승격했다.

T18/T19에서는 공개 hash-regex와의 차이를 family×tier로 다시 분해했다. 손실은
Premium의 `sym_math`와 `code_io`에 집중됐다. 기존 보조 헤드의 조건부 혼합은
fold 효과가 혼재해 기각했고, 두 family 안에서만 별도 64-bin hashed ridge를
학습해 Premium 전역 예측과 75% 혼합했다. 비활성 family의 예측은 T17과 완전히
같다. T19는 T17 대비 4/5/6/8-fold, Dev, LOFO가 모두 상승했고 0/36,000 및
전체 컨테이너 검증을 통과했다. 다만 작은 nested inner에서는 T17과 T19가 모두
0점이므로 nested 일반화 개선은 주장하지 않는다.

정직하게 적으면, 점수 상승의 **대부분은 모델링 아이디어가 아니라 구현 결함을
고친 데서 나왔다.** 임베딩 도입, 동점 탐지기, 확률 제약 배분 등 네 갈래는
모두 효과가 없거나 가설이 반증되어 버렸다. 반면 중복 프롬프트가 갈라져
배분되던 문제, 로그 예측의 외삽 폭주, 합계 편향, 교차검증이 폴드마다 예산을
쪼개던 문제를 고친 것이 실제 점수를 올렸다.

안전 손잡이는 실패 trial에서 실제로 반복된 경로에만 둔다. `code_io`와 catch-all
`other`의 K1 차단, Premium 상대비용 cap은 공개 Dev 손실이 거의 없지만 극단
재표집의 단일 문항 비용 폭주를 제거했다. 각 손잡이의 효과는 append-only 실험
로그와 LOFO 결과로 남겼다.

## 5. 실행과 재현

이미지는 네트워크 없이, 읽기 전용 루트 파일 시스템에서, UID 65532로 돈다.
학습은 하지 않고 이미지에 굳혀 넣은 계수만 읽는다.

| 항목 | 측정값 | 한도 | 사용률 |
| --- | ---: | ---: | ---: |
| 압축 계층 합계 | 63.4 MiB | 1024 MiB | 6.2% |
| rootfs 겉보기 크기 | 195.8 MiB | 2048 MiB | 9.6% |
| 실행 시간 (2,640문항, 최장) | 8.116초 | 90초 | 9.0% |

측정은 공식 도구(`router-measure-image`, `tools/check_runtime.py`)로 했다.
제출 절차 전체는 저장소의 `plan/RELEASE.md`에 있다.

어떤 예외도 등급을 죽이지 않도록, 프로세스 시작 직후 유효한 결정을 먼저
확보하고 예측이 실패하면 그대로 낸다. 시간 예산의 60%가 지나면 계산을 접는다.

## 6. 필수 기재 항목

### 프로젝트 등록 URL

```
⬜ https://github.com/chjnett/ossp-2026-llm-router-challenge/tree/<40자리 커밋 SHA>
```

`submission-ossp-skt.json`을 담은 커밋의 스냅샷이어야 한다. 브랜치 URL이나
움직일 수 있는 기본 브랜치 URL은 안 된다.

### 이미지

```
⬜ <레지스트리>/ossp-router@sha256:<64자리>
```

태그가 아니라 전체 다이제스트. `linux/arm64`.

### SBOM

저장소의 [`container/sbom.cdx.json`](../container/sbom.cdx.json).
CycloneDX 1.5, 구성요소 108개 (Debian 105, Python 2, 참가자 1).

이미지 안의 dpkg 데이터베이스와 Python dist-info를 직접 읽어 만든다. 기반 OS
패키지의 라이선스 근거는 이미지 안 `/usr/share/doc/<패키지>/copyright`에
105개 전부 보존되어 있다.

### AI 모델 활용·라이선스

```
해당 없음 — 실행 이미지에 AI 모델을 탑재하지 않음
```

라우터는 능형회귀 계수(85.9 KB JSON)만 사용한다. 신경망 가중치, 사전학습
모델, 토크나이저를 포함하지 않는다. 실행 중 어떤 모델도 호출하지 않는다.

### AI 코딩 도구 사용 범위

```
⬜ 아래 내용을 확인하고 조정할 것
```

Anthropic Claude Code(Claude Opus)와 OpenAI Codex를 사용했다. 사용 범위는
다음과 같다.

- 설계 검토, 구현, 테스트 작성, 문서 작성 전반
- 실험 설계와 결과 해석
- 최종 판단, 실험 채택 여부, 제출 결정은 참가자가 했다

생성한 코드는 전부 참가자가 검토했으며 379개 테스트와 공식 채점기로 검증했다.

### 데모 영상 URL

```
⬜ <영상 URL>
```

1. `docker run`으로 세 등급을 돌려 `submission.json`이 나오는 것
